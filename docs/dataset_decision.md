# DermAI — Database Schema

## 1. Overview

**Database:** PostgreSQL  
**ORM:** SQLAlchemy  
**Schema status:** Initial design for Milestone 1

This document defines the database tables, columns, data types, constraints, and relationships for DermAI.
The initial schema covers `users`, `cases`, and `images`. The `analyses` table and other model-related tables will be designed for later milestones when their requirements are implemented.

## 2. Users Table

### Purpose

The `users` table stores registered account information and access roles. Passwords must be stored as secure hashes, never as plain text.

### Table Definition

| Column | Data Type | Nullable | Constraints / Default | Description |
|---|---|---|---|---|
| `id` | UUID | No | Primary Key; generated UUID | Unique identifier for each user |
| `username` | VARCHAR(50) | No | None | User's display name |
| `email` | VARCHAR(255) | No | UNIQUE | User's email address |
| `password_hash` | VARCHAR(255) | No | None | Secure hash of the user's password |
| `role` | `user_role_enum` | No | DEFAULT `'user'` | User's assigned role |
| `created_at` | TIMESTAMPTZ | No | DEFAULT current timestamp | Account creation date and time |

### Role Enum

Enum name: `user_role_enum`

| Value | Description |
|---|---|
| `user` | General user |
| `clinician` | Clinician |
| `researcher` | Medical researcher |
| `data_scientist` | Data scientist or ML engineer |
| `admin` | Administrator |

### Constraints and Design Decisions

1. `id` is the primary key and uniquely identifies each account.
2. `email` must be unique to prevent multiple accounts from using the same email address.
3. `username`, `email`, `password_hash`, `role`, and `created_at` are required fields.
4. `role` is restricted to the values defined in `user_role_enum`.
5. The default role is `user`.
6. `created_at` uses a timezone-aware timestamp and is generated by the database.
7. `password_hash` stores a password hash, not the original password.
8. No foreign keys are required in this table at this stage.

### Future Relationships

- One user can own multiple cases through `cases.owner_user_id`.
- The relationship will be one-to-many: `users.id` → `cases.owner_user_id`.

### Implementation Status

**Design stage:** Defined in this document.  
**Database implementation:** To be completed and verified separately.  
**Authentication:** Password hashing, login, and role-based authorization will be implemented in their respective tasks.

## 3. Cases Table

### Purpose

The `cases` table stores skin examination cases created by users. Each case belongs to one user and may contain multiple uploaded images.

### Table Definition

| Column | Data Type | Nullable | Constraints / Default | Description |
|---|---|---|---|---|
| `id` | UUID | No | Primary Key; generated UUID | Unique identifier for each case |
| `owner_user_id` | UUID | No | Foreign Key → `users.id`; NOT NULL | User who owns the case |
| `case_label` | VARCHAR(100) | No | NOT NULL | User-provided label for the case |
| `body_location` | VARCHAR(100) | Yes | NULL allowed | Body location, if provided |
| `image_source` | VARCHAR(30) | No | NOT NULL | Source of the image, such as mobile upload |
| `status` | VARCHAR(30) | No | DEFAULT `'created'` | Current case workflow status |
| `created_at` | TIMESTAMPTZ | No | DEFAULT current timestamp | Case creation date and time |

### Constraints and Design Decisions

1. `id` is the primary key.
2. `owner_user_id` references `users.id`, ensuring each case belongs to an existing user.
3. `case_label` is required to identify the case.
4. `body_location` is optional because the user may not know or wish to specify the location.
5. `image_source` records how the image was obtained.
6. `status` tracks the case workflow and defaults to `created`.
7. `created_at` is generated by the database.
8. Deletion behavior for user-owned cases must be decided before implementing foreign-key actions.

### Relationships

- One user can own multiple cases.
- Each case belongs to exactly one user.
- Relationship: `users.id` → `cases.owner_user_id` (one-to-many).

### Implementation Status

**Design stage:** Defined in this document.  
**Database implementation:** To be completed and verified separately.

The allowed values for `image_source` and `status` must be finalized before implementation. The values above are initial design choices, not a claim that the requirements document mandates these exact values.


## 4. Images Table

### Purpose

The `images` table stores metadata and storage references for images uploaded to a case. Image files are stored separately from PostgreSQL; the database stores their paths and metadata.

### Table Definition

| Column | Data Type | Nullable | Constraints / Default | Description |
|---|---|---|---|---|
| `id` | UUID | No | Primary Key; generated UUID | Unique image identifier |
| `case_id` | UUID | No | Foreign Key → `cases.id`; NOT NULL | Case to which the image belongs |
| `original_path` | VARCHAR(500) | No | NOT NULL | Storage path of the original image |
| `processed_path` | VARCHAR(500) | Yes | NULL allowed | Storage path of a processed image, if available |
| `mime_type` | VARCHAR(100) | No | NOT NULL | Image media type, such as `image/jpeg` |
| `file_size_bytes` | BIGINT | No | NOT NULL; must be greater than zero | Image file size in bytes |
| `width` | INTEGER | No | NOT NULL; must be greater than zero | Image width in pixels |
| `height` | INTEGER | No | NOT NULL; must be greater than zero | Image height in pixels |
| `checksum` | VARCHAR(64) | Yes | NULL allowed | Optional SHA-256 checksum for file integrity and duplicate detection |
| `created_at` | TIMESTAMPTZ | No | DEFAULT current timestamp | Image upload record creation time |

### Constraints and Design Decisions

1. `id` is the primary key.
2. `case_id` references `cases.id`.
3. `original_path` identifies where the original image file is stored.
4. `processed_path` is optional because preprocessing may not have occurred yet.
5. `file_size_bytes`, `width`, and `height` must be positive.
6. `mime_type` records the image's media type; actual file validation must also be performed by the backend.
7. `checksum` is optional and may be used to help identify duplicate files.
8. `created_at` is generated by the database.
9. Image files are stored outside PostgreSQL; their metadata and paths are stored in this table.

### Relationships

- One case can contain multiple images.
- Each image belongs to exactly one case.
- Relationship: `cases.id` → `images.case_id` (one-to-many).

### Implementation Status

**Design stage:** Defined in this document.  
**Database implementation:** To be completed and verified separately.

The storage path format and image-validation rules will be finalized during the image-upload task.


## 5. Entity Relationship Diagram (ERD)

The initial DermAI database consists of three core entities: `users`, `cases`, and `images`.

```mermaid
erDiagram
    USERS ||--o{ CASES : owns
    CASES ||--o{ IMAGES : contains
```

### Relationship Explanation

1. **Users → Cases:** One user may own zero or more cases. Each case must belong to exactly one user.
2. **Cases → Images:** One case may contain zero or more images. Each image must belong to exactly one case.
3. **Primary keys:** `users.id`, `cases.id`, and `images.id`.
4. **Foreign keys:** `cases.owner_user_id` references `users.id`; `images.case_id` references `cases.id`.

The `analyses` entity and its relationships will be added when the analysis workflow is designed in a later milestone.
